# Replaceable runtime security assembly — candidate, disabled

The optional `runtime_security.py` module is called by the existing private Docker entry point before log rewriting and the original physical dispatch receipt. It neither allocates resources nor changes the SDK, Gateway, Runtime, Codex permission mapping, or account flow. Existing deployments without the new flags retain their behavior.

Enable only with both `--runtime-security-manifest` and `--runtime-security-sha256`, plus all existing physical-confirmation arguments. The pinned manifest must exactly match the entry point's image IDs, user and workspace root. Schema and operator configuration are specified in [the configuration contract](RUNTIME_SECURITY_CONTRACT.md). All policy files must be operator-owned, regular, single-link, non-symlink and not group/world writable. Their exact hashes are checked before dispatch. AppArmor must already be loaded under a dedicated name in enforce mode; the module never loads host policy or changes global sysctls.

The adapter sends seccomp JSON contents to the Docker API, drops all capabilities, requires no-new-privileges, and rejects conflicting caller privileges, devices, namespace sharing and kernel-path overrides. Policy changes fail closed. The original receipt records the manifest hash; there is no new lifecycle or state database. An AppArmor name or Docker label alone does not prove the effective kernel policy. Deployment must retain policy-loading, OCI and process evidence.

**Do not enable this candidate for real accounts yet.** On the isolated host, the fixed Codex CLI 0.163.0 executed successfully with the dedicated policies and rejected writes outside the workspace, but read a synthetic control file outside it, both directly and through a symlink. Workspace-write is not a confidentiality boundary. No real credentials were read. Fix and verify the trusted-service versus command credential boundary before activation.

`codex_sandbox_probe.py` uses temporary data, a clean environment, isolated HOME/CODEX_HOME and no model calls. It checks execution, workspace writes, denied external writes and denied direct/link reads of a synthetic control marker. Exit 1 means an incomplete boundary; exit 2 means a configuration/version/runtime error. A local probe pass cannot replace original-chain, UI, Provider, network, credential and lifecycle acceptance. The validated CLI syntax is `codex sandbox -- ...`, without a `linux` subcommand.

Negative checks accept only explicit EACCES/EPERM from the probe child (also EROFS for writes). Missing files, marker mismatch, command failures and namespace failures are not successful isolation. The revised probe has local regression coverage; previous remote evidence belongs to its recorded script version.

On 2026-11-12, the fixed isolated configuration passed original-chain lifecycle and Native/Codex real-model UI acceptance. This does not close credential isolation or validate other Providers. For a new workspace, merge [the explicit Default fragment](runtime-permissions.yaml.example) through the existing config path before model calls; do not replace existing config or user choices. Check config.get, UI and effective Provider settings (Codex workspace-write/on-request). The fragment is not auto-loaded or a complete config.

A test model key was found in a Codex shell snapshot and the task-owned copy was removed. Cleanup is not an isolation fix. Platform long-lived secrets must not enter executable config, child environments or session artifacts; scoped grants still need target, purpose, epoch, expiry and revocation limits. Environment filtering or disabling snapshots alone is insufficient.

Roll back only task-owned deployments after stopping new dispatch and reconciling through the original chain. Preserve unknown receipts and user data. Do not unload a profile still in use. Restoring the previous configuration restores previous capability; it does not resolve the sandbox limitation. Native infrastructure support may replace this adapter after equivalent acceptance, without changing account or Runtime ownership. No default service template enables this candidate.
